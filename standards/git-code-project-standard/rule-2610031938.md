# The Rosinfotech Base Standards

## The Git Code Project Standard

### Makefile

#### Rule #2610031938

* Context:

  * A project must not depend on a globally linked makefile of a particular machine - CI and colleagues need the framework scripts inside the repository;

* Description:

  * The makefile framework ([rosinfotech/makefile](https://github.com/rosinfotech/makefile)) is embedded into the project by the vendoring procedure ([vendor.sh](https://github.com/rosinfotech/makefile/blob/main/.makefile/vendor.sh));

  * The procedure:

    * runs from a clone of the makefile repository: `make vendor <project-path>`;

    * creates `.makefile/vendor/rosinfotech/` - the framework scripts with a README manifest (the source repository, the commit, the update and remove hints); the directory is fully managed - it is replaced wholesale on every run and is never edited by hand;

    * prepends the standalone definitions block to the project Makefile - marker-guarded, backed up; on later runs the block is upgraded to the current template;

    * scaffolds a minimal project when the target has no Makefile:

      * `Makefile` with the standalone block;

      * `.version`, `CHANGELOG.md`, `README.md`;

      * `.editorconfig` ([Rule #2610031936](/standards/git-code-project-standard/rule-2610031936.md));

    * validates the result with the system make and restores the backup / removes the vendor directory on failure;

  * Refreshing:

    * `git pull` in the makefile clone;

    * `make vendor <project-path>` again - the vendor directory is replaced wholesale; project scripts in `.makefile/` are never touched;

  * `vendor.sh` itself is never vendored - refreshing a project is possible only from a clone of the makefile repository;

* Benefits:

  * Independence from the globally linked make - the project builds and commits anywhere;

  * Reproducible CI - the scripts live in the repository;

  * The explicit source commit in the manifest - the provenance is auditable.

* Examples:

  * Case #1 - a fresh project:

    * the agent clones `rosinfotech/makefile`, runs `make vendor ~/projects/new-service`, and gets the scaffold: the Makefile with the standalone block, `.makefile/vendor/rosinfotech/`, `.version`, `CHANGELOG.md`, `README.md`, `.editorconfig`;

  * Case #2 - an existing project:

    * the framework is outdated - the agent pulls the makefile clone and re-runs `make vendor <path>`: the vendor directory is replaced, the Makefile block upgraded, the backup kept.
