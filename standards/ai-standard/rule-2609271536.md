# The Rosinfotech Base Standards

## The AI Standard

### AGENTS.md

#### Rule #2609271536

* Context:

  * TypeScript backend services on Node.js need a role profile that fixes the language toolchain and keeps the agent inside the backend boundary.

* Description:

  * The TypeScript (NodeJS) Backend Engineer AGENTS.md is a role file: it extends the BASE AGENTS.md ([Rule #2609271528](/standards/ai-standard/rule-2609271528.md)) and never weakens it; the ready-to-copy source of truth is the asset [AGENTS-STANDARD-BACKEND-TYPESCRIPT.md](/standards/ai-standard/assets/AGENTS-STANDARD-BACKEND-TYPESCRIPT.md);

  * Role scope: backend services, background workers and CLIs in TypeScript on Node.js - API implementation, business logic, data access, integration clients, tests; frontend and infrastructure work stay outside the role;

  * The npm scripts in package.json are the single source of commands: install, lint, format, type-check (`tsc --noEmit`), tests (the configured runner), build, run - the agent takes the exact commands from the project package.json and Makefile, never invents them;

  * The Node.js and npm version requirements are project decisions - the agent reads them from the repository (package.json engines, the Makefile); the role file stays version-neutral;

  * The code follows the Common Code Style Standard rules applicable to TypeScript on Node.js: [Rule #2103051010](/standards/common-code-style-standard/rule-2103051010.md) (UTLBL), [Rule #2103052001](/standards/common-code-style-standard/rule-2103052001.md) (from general to specific), [Rule #2108211519](/standards/common-code-style-standard/rule-2108211519.md) (abbreviations in uppercase), [Rule #2601190149](/standards/common-code-style-standard/rule-2601190149.md) (directories: kebab case), [Rule #2601190212](/standards/common-code-style-standard/rule-2601190212.md) (backend files: camel case + suffix), [Rule #2601190214](/standards/common-code-style-standard/rule-2601190214.md) (bash files: snake case), the path and file variable suffixes [Rule #2108211636](/standards/common-code-style-standard/rule-2108211636.md), [Rule #2108211643](/standards/common-code-style-standard/rule-2108211643.md), [Rule #2108211646](/standards/common-code-style-standard/rule-2108211646.md), [Rule #2108211652](/standards/common-code-style-standard/rule-2108211652.md), [Rule #2108211659](/standards/common-code-style-standard/rule-2108211659.md), [Rule #2109011651](/standards/common-code-style-standard/rule-2109011651.md) (function arguments: up to 3 required + options object), [Rule #2605280101](/standards/common-code-style-standard/rule-2605280101.md) (type prefixes I, T, E, G), [Rule #2605280102](/standards/common-code-style-standard/rule-2605280102.md) (unused: underscore prefix), [Rule #2609270950](/standards/common-code-style-standard/rule-2609270950.md) (indentation: 4 spaces), [Rule #2609270952](/standards/common-code-style-standard/rule-2609270952.md) (TSV over CSV);

  * Stack specifics (framework, test runner, DB access layer, migration tool) are project decisions - the agent reads them from the repository itself (package.json, Makefile, build config), never invents or replaces them;

  * Placement: the user-global agent config and/or the repository root.

* Benefits:

  * The agent always runs the project-configured scripts instead of guessing commands;

  * The role boundary prevents a backend agent from drifting into frontend or infrastructure work;

  * Project stack changes never require role file edits.

* Examples:

  * Case #1:

    * Incorrect:

      * the agent runs `jest` in a repository whose package.json defines `vitest`;

    * Correct:

      * the agent reads the test script from package.json and runs what the project defines.
