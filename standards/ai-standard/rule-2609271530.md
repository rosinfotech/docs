# The Rosinfotech Base Standards

## The AI Standard

### AGENTS.md

#### Rule #2609271530

* Context:

  * Design tasks require a specialized agent profile: a general-purpose agent mixes design and implementation concerns and produces unstructured, unreviewable decisions.

* Description:

  * The Architect AGENTS.md is a role file: it extends the BASE AGENTS.md ([Rule #2609271528](/standards/ai-standard/rule-2609271528.md)) and never weakens it; the ready-to-copy source of truth is the asset [AGENTS-STANDARD-ARCHITECT.md](/standards/ai-standard/assets/AGENTS-STANDARD-ARCHITECT.md);

  * The architect agent designs at both scales:

    * a whole project:

      * system decomposition into services and the boundaries between them;

      * the technology stack per area;

      * repository structure and bootstrapping;

      * cross-cutting concerns (configuration, logging, observability, security);

    * an individual microservice:

      * its boundaries and responsibilities;

      * the API contract with neighboring services;

      * the data model and the storage choice;

      * dependencies, failure and scaling modes;

  * Every design artifact follows the Documentation Standard:

    * structured descriptions with progressive disclosure ([Rule #2609270954](/standards/documentation-standard/rule-2609270954.md));

    * references pinned to commit and lines ([Rule #2609270956](/standards/documentation-standard/rule-2609270956.md));

  * Design artifacts follow the language-independent rules of the Common Code Style Standard:

    * [Rule #2103051010](/standards/common-code-style-standard/rule-2103051010.md) - UTLBL - unique sortable labels;

    * [Rule #2103052001](/standards/common-code-style-standard/rule-2103052001.md) - from general to specific;

    * [Rule #2108211519](/standards/common-code-style-standard/rule-2108211519.md) - abbreviations in uppercase;

    * [Rule #2601190149](/standards/common-code-style-standard/rule-2601190149.md) - directories: kebab case - repository structure;

    * [Rule #2610031256](/standards/common-code-style-standard/rule-2610031256.md) - collections: alphabetical sorting;

    * [Rule #2610031272](/standards/common-code-style-standard/rule-2610031272.md) - markdown lists: indentation step 2;

    * [Rule #2609270952](/standards/common-code-style-standard/rule-2609270952.md) - TSV over CSV;

  * The language-specific rules apply through the engineering roles;

  * The design output stays abstract about infrastructure ([Rule #2609270958](/standards/security-standard/rule-2609270958.md)):

    * no IPs;

    * no ports;

    * no hostnames - server codenames only;

  * The architect proposes - implementation starts only on an explicit order (the base rules apply unchanged);

  * The concrete constraints of the target system come from the repository itself (its build config, its installed stack) - the design never invents a stack that contradicts them;

  * Placement: the user-global agent config and/or the repository root of the designed project.

* Benefits:

  * One agent profile covers both greenfield projects and single-service evolution;

  * Design decisions are structured, referenced and reviewable;

  * Design and implementation stay separated.

* Examples:

  * Case #1 - a whole project:

    * the agent decomposes an admin platform into an API gateway, an auth service, two business services and a web frontend, with the stack choice per area and the boundary contracts;

  * Case #2 - an individual microservice:

    * the agent designs a notification service: the REST plus queue API contract, the data model, the dependency on the user service and its failure modes.
