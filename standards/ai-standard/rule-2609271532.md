# The Rosinfotech Base Standards

## The AI Standard

### AGENTS.md

#### Rule #2609271532

* Context:

  * Go backend services need a role profile that fixes the language toolchain and keeps the agent inside the backend boundary.

* Description:

  * The Go Backend Engineer AGENTS.md is a role file: it extends the BASE AGENTS.md ([Rule #2609271528](/standards/ai-standard/rule-2609271528.md)) and never weakens it; the ready-to-copy source of truth is the asset [AGENTS-STANDARD-BACKEND-GO.md](/standards/ai-standard/assets/AGENTS-STANDARD-BACKEND-GO.md);

  * Role scope: backend services, background workers and CLIs in Go - API implementation, business logic, data access, integration clients, tests; frontend and infrastructure work stay outside the role;

  * The file fixes the Go toolchain: build `go build ./...`, vet `go vet ./...`, tests `go test ./...`, formatting `gofmt` plus the project linter when configured (e.g. golangci-lint) - the exact commands must match the project Makefile;

  * Go formatting follows gofmt: its output (tabs) wins over the general indentation rule ([Rule #2609270950](/standards/common-code-style-standard/rule-2609270950.md)) - the formatter is never reconfigured;

  * The code follows idiomatic Go plus the Common Code Style Standard rules applicable to Go: [Rule #2103051010](/standards/common-code-style-standard/rule-2103051010.md) (UTLBL), [Rule #2103052001](/standards/common-code-style-standard/rule-2103052001.md) (from general to specific), [Rule #2108211519](/standards/common-code-style-standard/rule-2108211519.md) (abbreviations in uppercase), [Rule #2601190149](/standards/common-code-style-standard/rule-2601190149.md) (directories: kebab case), [Rule #2601190214](/standards/common-code-style-standard/rule-2601190214.md) (bash files: snake case), the path and file variable suffixes [Rule #2108211636](/standards/common-code-style-standard/rule-2108211636.md), [Rule #2108211643](/standards/common-code-style-standard/rule-2108211643.md), [Rule #2108211646](/standards/common-code-style-standard/rule-2108211646.md), [Rule #2108211652](/standards/common-code-style-standard/rule-2108211652.md), [Rule #2108211659](/standards/common-code-style-standard/rule-2108211659.md), [Rule #2109011651](/standards/common-code-style-standard/rule-2109011651.md) (function arguments: up to 3 required + options object), [Rule #2609270950](/standards/common-code-style-standard/rule-2609270950.md) (indentation; in Go source gofmt wins), [Rule #2609270952](/standards/common-code-style-standard/rule-2609270952.md) (TSV over CSV); the backend file naming rule [Rule #2601190212](/standards/common-code-style-standard/rule-2601190212.md) is excluded - it covers Java and JavaScript/TypeScript;

  * Stack specifics (HTTP framework, DB driver, migrations tool, Go version) are project decisions - the agent reads them from the repository itself (go.mod, Makefile, build config), never invents or replaces them;

  * Placement: the user-global agent config and/or the repository root.

* Benefits:

  * The agent always runs the language-idiomatic toolchain instead of guessing commands;

  * The role boundary prevents a backend agent from drifting into frontend or infrastructure work;

  * Project stack changes never require role file edits.

* Examples:

  * Case #1:

    * Incorrect:

      * the role file pins `gin` as the HTTP framework, so a `net/http` project gets refactored against its own decision;

    * Correct:

      * the role file fixes only the toolchain; the framework comes from the concrete repository (go.mod, the Makefile).
